1. Portada y Presentación del Proyecto

mapCarga: Sistema de Optimización de Rutas de Transporte

Diseño e implementación de un sistema de cálculo de rutas óptimas para transporte de carga en el Gran Chaco mediante computación paralela y distribuida.

  • Región: Conectividad vial internacional entre Bolivia, Argentina y Paraguay (corredor bioceánico por Yacuiba).
  • Algoritmo Base: Dijkstra con búsqueda de rutas alternativas (Yen simplificado).
  • Enfoques: Secuencial, OpenMP (memoria compartida) y OpenMPI (distribuida).
  • Infraestructura: Clúster Docker de 3 nodos (Master + 2 Workers).
+-------------------------------------------------------------+ | SISTEMA DE TRANSPORTE MULTINODO | | | | [ Grafo Vial ] ---> Ciudades (Nodos) y Rutas (Aristas) | | [ Consultas ] ---> 100, 1.000 y 10.000 pares Origen-Dest | | | | [ Secuencial ] ---> Línea Base T(1) | | [ OpenMP ] ---> #pragma omp parallel for (Multi-core) | | [ OpenMPI ] ---> Clúster 3 Nodos (Master + W1 + W2) | +-------------------------------------------------------------+

2. Planteamiento: Grafo de Transporte y Dijkstra
Tiempo estimado: 1:00 min

Estructura del Problema Logístico:

  • Grafo Ponderado $G = (V, E)$:
    • $V$: Ciudades (Yacuiba, Villamontes, Tartagal, Asunción, Santa Cruz, etc.).
    • $E$: Conexiones viales con atributos de distancia ($km$), tiempo ($h$) y peajes.
  • Consultas Batch ($Q$): Pares (Origen, Destino) que demandan la ruta óptima.
  • Conjuntos de Prueba Evaluados:
    • Small: 25 ciudades, 29 rutas, 100 consultas.
    • Medium: 200 ciudades, 799 rutas, 1.000 consultas.
    • Large: 200 ciudades, 799 rutas, 10.000 consultas masivas.
Estructura de la Consulta en C++ (src/common/route.hpp):
struct Query { int id; std::string origin; std::string destination; }; struct RouteResult { double total_distance; double total_time; std::vector<std::string> path; bool found; };
🗣️ Lo que tienes que decir en la defensa:
"El sistema modela la red vial del Gran Chaco como un grafo dirigido ponderado donde los vértices son ciudades y las aristas son carreteras internacionales con distancias y tiempos de viaje. El desafío computacional no es calcular una sola ruta, sino resolver ráfagas de cientos o miles de consultas simultáneas que llegan al centro de control. Cada consulta ejecuta Dijkstra buscando la ruta más corta y hasta 3 rutas alternativas por si existen bloqueos de carretera. Como cada consulta tiene su propio origen y destino, las consultas son completamente independientes entre sí. Esto clasifica al sistema como Embarrassingly Parallel a nivel de lote de consultas."

4. OpenMP en Transporte: Código y Mecánica de Paralelización
Tiempo estimado: 1:30 min

Código C++ en src/openmp/main.cpp:

// Asignar el número de hilos solicitado por parámetro omp_set_num_threads(num_threads); int total_queries = queries.size(); std::vector<QueryResult> results(total_queries); double start_time = omp_get_wtime(); // DIRECTIVA MAESTRA DE PARALELIZACIÓN: #pragma omp parallel for schedule(dynamic) for (int i = 0; i < total_queries; i++) { results[i].query = queries[i]; // Cada hilo ejecuta su propia instancia de Dijkstra results[i].alternatives = find_alternative_routes( graph, queries[i].origin, queries[i].destination, K_ALTERNATIVES ); } double elapsed = omp_get_wtime() - start_time;

¿Por qué este código no tiene Condiciones de Carrera?

  1. Escritura Exclusiva: El hilo que procesa la consulta i escribe únicamente en la celda results[i]. No hay solapamiento de memoria.
  2. Grafo Read-Only: El grafo vial es compartido pero de solo lectura; ningún hilo muta la topología vial.
  3. Colas Locales: Las colas de prioridad y arreglos de distancias de Dijkstra se instancian en el stack local de cada hilo.

¿Por qué schedule(dynamic) y no static?

A diferencia de un cálculo aritmético fijo, en Dijkstra el tiempo de búsqueda varía según la distancia entre origen y destino: una ruta vecina tarda microsegundos, mientras que cruzar el mapa de frontera a frontera explora cientos de nodos. Con schedule(dynamic), el hilo que termina rápido toma la siguiente consulta disponible, garantizando un balanceo de carga óptimo.

🗣️ Lo que tienes que decir en la defensa:
"En la versión OpenMP atacamos el problema distribuyendo el lote de consultas entre los hilos del procesador. Como ven en el código de openmp/main.cpp, usamos #pragma omp parallel for schedule(dynamic). Aquí hay dos decisiones de diseño fundamentales que cualquier docente de sistemas paralelos evaluará: Primero: ¿Por qué no hay condiciones de carrera si no usamos mutex? Porque el vector results tiene el tamaño preasignado y la iteración i solo escribe en la posición results[i], mientras que el grafo se comparte en modo de solo lectura. Segundo: ¿Por qué usamos schedule(dynamic)? Porque el algoritmo de Dijkstra no tiene tiempo uniforme: encontrar la ruta entre Yacuiba y Villamontes tarda unos microsegundos, pero entre Santa Cruz y Asunción recorre muchas más ciudades. La planificación dinámica evita que un hilo quede ocioso esperando a otro que procesa una ruta larga."

6. Comparativa con OpenMPI (Memoria Distribuida)
Tiempo estimado: 1:15 min

Lógica de Distribución MPI (src/mpi/main.cpp):

  • Serialización: El Rank 0 empaqueta el grafo vial en un buffer continuo y lo difunde con MPI_Bcast.
  • Distribución de Consultas: Cada nodo recibe un subrango continuo $N / P$ del total de consultas.
  • Recopilación: Los tiempos y rutas encontradas se consolidan en el Rank 0 mediante MPI_Gather / MPI_Reduce.

Resultados Reales de MPI en Clúster (Dataset Large - 10k consultas):

ProcesosNodos ClústerTiempo PromedioSpeedup

*Con 3 nodos distribuidos en red, el clúster completa 10.000 consultas en solo 2.52 segundos (Speedup de 2.75x).

🗣️ Lo que tienes que decir en la defensa:
"Al comparar OpenMP con OpenMPI, observamos la diferencia entre memoria compartida y memoria distribuida. En MPI no compartimos memoria RAM; el nodo Master debe difundir el grafo vial a los workers mediante MPI_Bcast y luego repartir las consultas. En el dataset Large de 10.000 consultas, cuando activamos los tres nodos del clúster (Master, Worker1 y Worker2), el tiempo cae de 6.96 segundos a 2.52 segundos, alcanzando un Speedup de 2.75x a través de la red virtual de Docker. Esto demuestra que para volúmenes masivos de transporte, el clúster distribuido ofrece una capacidad de escalamiento horizontal que ningún procesador mononodo puede igualar."
7. Análisis Teórico: Amdahl, Gustafson, Flynn y LogP
Tiempo estimado: 1:00 min

1. Ley de Amdahl (Fracción Serial)

$$S(p) = \frac{1}{f_s + \frac{1-f_s}{p}}$$ Con $S(2) = 1.948$ en 10.000 consultas: $f_s = \frac{2/1.948 - 1}{2 - 1} \approx 0.026$ (2.6%)

La fracción serial de lectura del archivo CSV y parsing es mínima (2.6%), lo que habilita un speedup teórico máximo de $S_{max} \approx 38\times$.

2. Gustafson, Flynn y Modelo LogP

  • Ley de Gustafson: Al escalar la red vial a nivel nacional o regional con miles de ciudades, el sistema incrementa su eficiencia paralelizable.
  • Taxonomía de Flynn: Clasifica como MIMD (múltiples flujos de instrucciones sobre diferentes orígenes/destinos).
  • Modelo LogP: La latencia de red ($L$) penaliza conjuntos pequeños, pero con 10.000 rutas el tiempo de cómputo domina plenamente sobre la red.
🗣️ Lo que tienes que decir en la defensa:
"El marco teórico confirma con rigor nuestros hallazgos: Aplicando la Ley de Amdahl sobre las 10.000 consultas de OpenMP, determinamos que la fracción serial es de apenas 2.6%, consistente en la lectura de los CSV. Esto confirma matemáticamente que el 97.4% del algoritmo de transporte es perfectamente paralelizable. Bajo la Taxonomía de Flynn, operamos en la categoría MIMD. Y el modelo LogP fundamenta el comportamiento de MPI: el retardo de inicialización de la red bridge explica por qué datasets pequeños no aceleran, mientras que en datasets masivos el clúster alcanza su régimen de alta eficiencia."
